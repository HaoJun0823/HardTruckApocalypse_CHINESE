# 资料片 Meridian113 汉化移植 与 LAA 崩溃修复

> **状态：两项均已完成并实机验证**（2026-10-08）。
> 实现：[HardTruckApocalypse_CHINESE_DLL_DLC1/](../HardTruckApocalypse_CHINESE_DLL_DLC1/)（汉化）、
> [DLC1_MemFix/](../DLC1_MemFix/)（内存修复）；交付包 [dist_dlc1/](../dist_dlc1/)。
>
> 一句话结论：
> **① 113 的字体/文本代码与本体 hta.exe 同源，但「地址、寄存器分配、结构体偏移」三者都不同**
> —— 必须逐点重新对齐，不能平移。
> **② 113 的 LAA 崩溃与本体的 `dxrender9+0x416D6` 是同一个签名（`road.fx` 的 effect 加载失败），
> 但修复点不同：本体在 `dxrender9.dll` 里，113 把渲染器静态链接进了 exe，因此要换
> `Kernel+0x30/0x34/0x38` 三个分配器指针。**

## 1. 两个 exe 的关系（先厘清，否则会平移错地址）

| | 本体 `hta.exe` | 资料片 `Meridian113.exe` |
|---|---|---|
| 大小 | 6,656,000 字节 | 9,342,976 字节 |
| ImageBase / 段数 | 0x400000 / 6 | 0x400000 / 5 |
| `DllCharacteristics` | — | **0**（无 ASLR、无 NX ⇒ 地址稳定） |
| 渲染器 | **外部** `dxrender9.dll`（1.78 MB） | **静态链接进 exe**（无 `dxrender9.dll` 字符串，只剩编译期源码路径 `dxrender9\device.h`） |
| 时间戳 | 0x43CF4131 (2006-01-19) | 0x4587A3A4 (2006-12-19) |

同目录下的 `htaroc.dat`（9,342,976 字节）**与 `Meridian113.exe` 同尺寸、同 PE 头，
但逐字节比对有 8,050,005 字节不同** —— 是另一个 build，不是同一个文件。汉化只需针对
`Meridian113.exe`。

> ⚠ 两个 exe 的**各段位移互不相干**，也不存在「加一个常数偏移」的换算关系。
> 全部锚点必须独立定位。

## 2. 汉化移植：113 与 hta 的逐点差异

### 2.1 锚点对照（全部已用 IDA + 离线 `sigtest` 双验证）

| 锚点 | hta.exe | Meridian113.exe | 定位方式 |
|---|---|---|---|
| 文本度量 | 0x685990 | 0x690A10 | 签名（唯一） |
| 文本绘制 | 0x685CA0 | 0x690D20 | 签名 + 消歧（113 命中 2 处，取 measure 之后最近者） |
| 运行时烘图 | 0x8B9350 | 0x7492D0 | 签名 |
| `Font::CreateFromXmlNode` | 0x8B80B0 | 0x747D40 | 签名 |
| `Font` 构造 | 0x8B6740 | 0x746350 | 签名 |
| P4 主查表 | 0x6865A2 | 0x691682 | 签名（唯一） |
| P4b 第二处查表 | 0x686A26 | 0x691B06 | 签名（唯一） |
| P5 主遍历 | 0x686A52 | 0x691B32 | 签名（唯一） |
| P5 的 4 条 rel32 跳入点 | 0x6864ED/507/58B/59C | 0x6915CD/5E7/66B/67C | 扫「目标 == P5+3」的 rel32 |
| P7 度量宽度 | 0x685B21 | 0x690BA1 | 签名（唯一） |
| P8 度量推进 | 0x685BD1 | 0x690C51 | 签名（唯一） |
| 度量循环头 / 退出 | 0x685A80 / 0x685C12 | 0x690B00 / 0x690C92 | 由 P8 指令流推导 |
| 冻结门（`Application::init` 出口） | 0x5AA388 | 0x6208C1 | 签名（唯一，**字节完全相同**） |
| `Application::init` | 0x5A9040 | 0x61E9C0 | 签名（唯一） |
| GfxServer 入口 | 0x6843F0 | 0x688C50 | 结构推导 |
| GfxServer 全局 | 0xA13CC0 | 0xC9BA10 | 结构反查① |
| uiCore 全局 | 0xA0A88C | 0xC7BA0C | 签名（唯一） |
| 引擎分配器包装 | 0x589410 | 0x5C0CE0 | 签名 + 结构唯一化② |
| `FontManager` 偏移 | `+0x4A4` | `+0x4A4` | **相同**（实测 `mov ecx,[edx+4A4h]`） |

① `GfxServer 全局`：扫 `8B 0D <imm32> ; … call rel32`，取 call 目标 == GfxServer 入口的那条
（113 的 xref 在 `sub_602BB4`：`mov ecx, dword_C9BA10 ; push edx ; call sub_688C50`）。

② `引擎分配器`：通用签名在 113 上有 **3 处命中**（0x5C0CE0 / 0x614B90 / 0x83F980），
本体只有 2 处、取首个恰好正确 —— 那是运气。113 必须把「它读的全局地址」写进签名来唯一化：
`8B 44 24 04 50 52 51 8B 0D 00 BA C7 00 E8 ?? ?? ?? ?? C2 04 00`。
依据是一条**结构不变式**：分配器读的全局恰好比 uiCore 全局低 `0xC`
（hta: `0xA0A880` vs `0xA0A88C`；113: `0xC7BA00` vs `0xC7BA0C`）。

### 2.2 代码层面的三处真实差异

| 差异 | hta | 113 |
|---|---|---|
| 绘制函数长度 | `0x685CA0..0x686B07`（0xE67） | `0x690D20..0x691BE7`（0xEC7）—— **多 0x60 字节**，P4 之后的地址整体 +0x60 |
| 预扫循环的索引寄存器 | `edi`：`83 C7 01 EB ??` | **`esi`**：`83 C6 01 EB ??`（这就是旧特征码在 113 上失配的原因） |
| P3 的后继指令 | `8B 46 18 83 F8 03` | `8B BC 24`（`mov edi,[esp+…]`） |
| P1 预扫索引 | `0F B6 0C 17`（`[edi+edx]`） | `0F B6 0C 16`（`[esi+edx]`） |

### 2.3 ★ 但有一点完全相同：裸汇编助手的栈偏移

这是移植成本最低的一条，也是必须**先验证再复用**的一条：

```
113 绘制函数内：
  [esp+0x34] = Font*            （P4 锚点 `8B 7C 24 34` 逐字节相同）
  [esp+0x54] = 文本基址指针
  [esp+0x6C] = strlen           （`3B 74 24 6C`）
113 度量函数内：
  [esp+0x4C] 当前字符 / [esp+0x1C] strlen /
  [esp+0x20] 文本基址指针 / [esp+0x10] Font* / [esp+0x14] 宽度累加器
```

P4/P4b/P5 的**签名字节完全一致**即证明这点，因此所有裸汇编助手（P4 查表、P4b 第二查表、
P5 双字节推进、P7/P8 度量）可以**原样复用**，只需改 `edi → esi` 那一处。

### 2.4 移植时踩的坑（已修，并加了回归断言）

`RVA_EngineCore` 我一开始写成了**绝对 VA**（`0xC7BA0C`）而不是 **RVA**（`0x87BA0C`）。
于是 `*(base + VA)` 读到模块外 → 启动即 `0xC0000005`。

> 教训：本体那行写的是 `0x60A88C`，看着像地址其实是 RVA（`0xA0A88C - 0x400000`）。
> **现在 `sigtest` 里加了一条断言**：`RVA_EngineCore == uiCore全局 − 0x400000`，
> 两个 exe 都校验，防止再犯。

## 3. LAA 崩溃：现场与根因

### 3.1 崩溃签名（4 份 dump 一致）

```
Exception : 0xC0000005 at 0x006FA2EA      (read attempt to address 0x00000000)
Registers : ESI = 00000000                 ← 崩因
            EDI = 0x8E93A840 / 0x82B286A0 / 0x93178FF8（均为 ≥2GB 的堆指针，残留值）
EIP 字节  : 8B 3E 8B CE FF 57 24  →  mov edi,[esi] / mov ecx,esi / call [edi+24h]
```

引擎日志最后一行（每次都是它）：

```
Kernel.cpp[0317] EffectImpl: failed to load fx file 'data\shaders\road.fx'
                 with: No D3DX error message.
```

这与本体当年的崩溃**是同一个签名**（[LAA 内存扩展崩溃](2026-10-07-LAA内存扩展崩溃-根因与Render9Fix.md)
里记的 `road.fx` technique 计数为 0 → 取 `techArr[0]`(NULL)）。

### 3.2 调用链（自写 minidump 栈回溯取证）

```
sub_6FA2C0  ← 0x6FA3BF  ← sub_6FA350  ← 0x6FB531 ← sub_6FB470 ← 0x6FEFFE ← sub_6FF080
   ↑ 崩在这
```

`sub_6FA350(this, 名称, 结构体)` 在拼 `"data/shaders/" + 名称 + ".fx"`，然后对 **4 个 32 字节槽位**
循环：读 `槽+0x1C`（std::string 之后的字段），传给它去解析。**奇数槽位**会解引用该指针：

```c
char __fastcall sub_6FA2C0(char a1, int a2, int a3) {   // a1 = 槽号
  if ((a1 & 1) != 0) {              // 奇数槽：需要指针有效
    if (!device->Check(25)) return 0;
    v5 = *(_DWORD *)a3;             // ← 崩：a3 == 0
    ...
```

⇒ 该槽的指针是 **NULL**，因为**这次 fx 加载失败**了（日志已明说），结构体没被填好。

### 3.3 为什么「≥2GB」这个假设成立

| 观察 | 说明 |
|---|---|
| 本体：不开 LAA 正常 / 开 LAA 崩 | 地址问题 |
| 本体：x32dbg 挂上或加 4ms 调试延迟就不崩 | 延迟不改变单线程计算，只改变**各线程分配交错** ⇒ 内存池布局变了 |
| 本体：单核 + LAA 仍崩 | 排除并发竞态 |
| 113：**间歇性**（同一机器 `ROC 0001` 那次就成功跑过了 `Roadset loaded`） | 布局/时序性，不是固定数据问题 |
| 113：汉化装配本身 100% 成功（`12 字号 × 2022 字，无缺失`） | 与汉化内容无关 |

## 4. 修复：`DLC1_MemFix`

### 4.1 为什么不能直接复用本体的 Render9Fix

本体 Render9Fix hook 的是 `dxrender9.dll` 的内部结构；113 **没有这个 DLL**。
但 113 的 `Kernel` 对象里有等价的三个分配器函数指针 —— 只是偏移不同。

### 4.2 113 的 Kernel 布局（IDA 实证）

`sub_5C3EE0` 就是 **`Kernel::Kernel`**（函数内含字符串 `.\Kernel.cpp`、`0 == g_Kernel`）：

```
+0x00  vtable      = off_BB78E0
+0x08  MemoryManager
+0x30  AllocMem    = sub_5C0CE0   ← 本体是 +0x18
+0x34  ReallocMem  = sub_5C0D10   ← 本体是 +0x1C
+0x38  FreeMem     = sub_5C0D00   ← 本体是 +0x20
全局： g_Kernel = dword_C7BA0C（RVA 0x87BA0C）
```

原始字节（0x5C3F4D 起）：

```
mov dword ptr [esi+30h], offset sub_5C0CE0
mov dword ptr [esi+34h], offset sub_5C0D10
mov dword ptr [esi+38h], offset sub_5C0D00
```

### 4.3 策略与安全闸

与 Render9Fix 同策略：**不 patch 任何代码指令**，只替换 3 个**数据指针**。
装之前两道闸，任一不过就什么都不做：

1. **逐条身份校验**：`+0x30/+0x34/+0x38` 三个值必须**恰好等于** IDA 期望的
   `0x5C0CE0 / 0x5C0D10 / 0x5C0D00`（把「布局猜错」的可能性彻底排除）；
2. **块头魔数探针**：实测一次「分配 64 字节 → 校验 → 释放」。

113 的块布局（`sub_5D5190` 反编译实证）：

```
user = block + 16
block[3]      = 0xDEADBEEF        （即 user-4）
*(user+size)  = 0xFEEBDAED        （尾哨）
```

探针日志实例：`块头 = [0x00000002 0x00000040 0x0002DC18 0xDEADBEEF] 尾哨 = 0xFEEBDAED`。

## 5. ★ 两个实现陷阱（v1 失败 → v2 成功，这是本文最有价值的部分）

| | v1（不生效） | v2（生效） |
|---|---|---|
| **低地址池大小** | 32 MB。实测**在世界加载前就满了**（`提交 33554432/33554432`），而世界加载在 6 秒之后 ⇒ **关键时刻一笔都导向不了**，`回退` 从 56647 涨到 85420 | **256 MB**，`回退` **恒为 0**，`提交 158MB/256MB` 余量充足 |
| **原块处理** | 我把它当成"安全设计"：导向后**故意不释放原块**。实测 64.6 万笔 ⇒ **约 100MB 高地址内存被泄漏**，反过来把引擎内存顶到更高地址、池也更快耗尽 | 用**配对的 `g_free` 把原块还回引擎**（`p` 本来就是 `g_alloc` 发的合法块，配对释放是安全的） |
| 结果 | `road.fx` 加载失败 → 崩（dump 0004，`mem used` 236 MB） | 连续 61+ 秒稳定、`导向 8513348 笔 / 868MB`、**不再产生新转储** |

> `g_free` 配对的安全性依据：`p` 由 `g_alloc` 发、`g_free` 正是同一个 `MemoryManager` 的
> 释放器（`sub_5C0D00` 会读块头 `[user-8]` 拿到 manager，再交给 `sub_5D52E0`）。
> 不是"随便调个 free"。

## 6. 诊断方法上的教训

1. **崩溃是间歇性的，不能用「一次没崩」当验证通过。**
   `ROC 0001`（22:45:03）就成功跑过了 `World loaded` → `Roadset loaded in: 239`，
   而 0002/0003/0004 三次都失败。**至少要连跑 2~3 次**才能判成败。
2. **别把推测当结论来驱动方案。** 我中途写过一句"机制与本体完全一致"，那是基于
   签名相似做的**推测**；拿它去写补丁，第一次就没打中。后来改成：
   先用 dump 栈回溯坐实调用链（`sub_6FA2C0 ← sub_6FA350 ← sub_6FB470`），再动手。
3. **对照实验比继续猜更有价值。** 三个对照直接改变了判断：本体日志**零** `EffectImpl` 错误、
   `ROC 0001` 成功、以及 MemFix v1/v2 的 `回退` 计数对比。
4. **日志要给出可判读的计数。** `回退 N 笔` 这一项直接把「池不够」暴露出来了 ——
   如果只记「成功/失败」，v1 的问题根本看不见。

## 8. 附带修的一个工具链问题

`fontgen/build_cjk.py` 用了 `tempfile.mkdtemp()`。Windows 上 Python 的
`os.mkdir(path, 0o700)` 会写出一个**显式限制性 DACL**，在受限环境下导致
`PermissionError`（目录建得出来、里面写不进文件，且事后连删都删不掉）。
改成 `os.makedirs`（默认 mode，不设 DACL），语义等价。**与游戏/汉化无关**，
只是让烘焙能在受限环境下跑。
