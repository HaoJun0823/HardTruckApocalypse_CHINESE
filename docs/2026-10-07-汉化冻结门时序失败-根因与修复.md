# 汉化冻结门：时序失败根因分析与修复

> **状态：两个 bug 均已修复，实机连续 3 次验证通过**（2026-10-07 21:18-21:19）。
> 修复位置：`HardTruckApocalypse_CHINESE_DLL/pathd.cpp`（三处）
> 相关：[PATH_D_DESIGN.md](../PATH_D_DESIGN.md)（路径 D 总设计）、
> [HardTruckApocalypse_CHINESE_DLL/README.md](../HardTruckApocalypse_CHINESE_DLL/README.md)
>
> 一句话结论：**冻结门在依赖未就绪时"立刻放弃"而不是"原地等"，
> 而热重启（prefetch 生效、引擎初始化变快）恰好把引擎推到门前 —— 只差 0.5~0.9 秒却已经弹框退出；
> 另外那个失败对话框用 `MessageBoxA` 显示 UTF-8 字面量，必然乱码。**

---

## 1. 症状

| 现象 | 细节 |
|---|---|
| 汉化失效 | 游戏能进，但完全没有中文（不是乱码，是没装上） |
| 失败对话框 | 标题 `Hard Truck Apocalypse - 汉化安装失败`，**正文全乱码** |
| 复现规律 | **冷启动（长时间没进游戏，加载慢）正常；连续热重启（加载变快）必失败** |
| 失败后行为 | 插件弹框告知玩家，玩家点确定后**主动退出进程**（设计如此，不留半装状态） |

玩家看到的乱码（原样）：

```
Hard Truck Apocalypse-姹久穿瀹菱口澶辫触
姹夂嶷淪羑ɪ澶辫触銆? …
```

**与 Render9Fix（LAA 崩溃修复）无关** —— 证据：2026-10-07 **11:00** 的
`hta_chs.20261007_110025.log`（在 20:54 部署 Render9Fix **之前**）就是同样的
「失败对话框 → 退出进程」。Render9Fix 只动 dxrender9 的分配，不碰字体/补丁路径。

## 2. Bug 1：失败对话框乱码

### 根因

本 DLL 编译带 `/utf-8`（见 vcxproj `<AdditionalOptions>/utf-8</AdditionalOptions>`），
所以源码里的中文字面量在二进制里是 **UTF-8 字节**。而旧代码用的是：

```cpp
// pathd.cpp:3093（旧）
MsgBoxA_t fn = (MsgBoxA_t)::GetProcAddress(u32, "MessageBoxA");
if (fn) fn(nullptr, msg, "Hard Truck Apocalypse - 汉化安装失败",
           MB_OK | MB_ICONERROR | MB_SETFOREGROUND | MB_TOPMOST);
```

`MessageBoxA` 按**系统 ANSI 代码页**（中文系统 = 936/GBK）解释这些字节 ⇒ 全乱码。

### 验证

把玩家看到的乱码按"UTF-8 字节被 GBK 解码"反向还原，正好得到源码里的原文：

| 乱码 | 原文 |
|---|---|
| `姹久穿瀹菱口澶辫触` | `汉化安装失败` |
| `璇峰皺璇暸噸鏂板萇鍔ㄦ父鎴?` | `请尝试重新启动游戏` |
| `hta_chs*.log` | `hta_chs*.log`（纯 ASCII，所以没乱） |

### 修复

改成显式把 UTF-8 转成 UTF-16，再交给 `MessageBoxW`（与代码页无关）：

```cpp
wchar_t wmsg[1024] = {0}, wtitle[128] = {0};
const int nMsg   = ::MultiByteToWideChar(CP_UTF8, 0, msg, -1, wmsg, 1024);
const int nTitle = ::MultiByteToWideChar(CP_UTF8, 0, "Hard Truck Apocalypse - 汉化安装失败",
                                         -1, wtitle, 128);
if (nMsg > 0 && nTitle > 0)
    fnW(nullptr, wmsg, wtitle, MB_OK | MB_ICONERROR | MB_SETFOREGROUND | MB_TOPMOST);
```

改动后 DLL 的导入表里出现 `MessageBoxW` 与 `MultiByteToWideChar` ✓。

## 3. Bug 2：冻结门"立刻放弃"

### 机制回顾

`pathd.cpp` 的方案 F：在 `Application::init` 的**成功出口**（`0x5AA388`，`mov eax,1`）
写一个跳转，进我们自己的代码洞 → 调 `PathD_InitExitGate()`。

此时引擎主线程**就停在这个函数里**，于是：

- 字体已全部建完（枚举 FontManager 必定成功）
- 尚未进入主循环（不可能有半装状态被引擎执行）
- 定位/写补丁/装配可以任意慢

而插件的 `Init()`（跑在 ASI 的 InitThread 上）只负责装门 + 备好依赖
（引擎分配器 / 包文件 / 字体管理器），备好后置 `g_initDepsReady = 1`。

### 两个失败模式

| 模式 | 日志特征 | 成因 |
|---|---|---|
| **F1** 门触发了，但依赖没就绪 | 有 `接管 Application::init 出口`，紧跟 `★Init 依赖尚未就绪，放弃★` → 弹框 | 门里是 `if (未就绪) { 弹框; return; }` —— **不等** |
| **F2** 门装得太晚 | 有 `[冻结门] ★已安装★` 但**完全没有 `接管` 行**，日志直接到 `插件卸载` | 装门要 `WriteBlockSafe` 挂起全部线程（实测 1.4~3.2 s），引擎已越过出口 ⇒ 门永不触发 ⇒ **静默无汉字，连弹框都没有** |

### 实证（F1 是"只差 0.83 秒"）

`hta_chs.20261007_210533.log`：

```
21:05:38.051  pathd: ╔═════════ [冻结门] 接管 Application::init 出口 ═════════
21:05:38.095  pathd: [冻结门] ★Init 依赖尚未就绪，放弃★（引擎比初始化线程先跑完了 Application::init）
21:05:38.122  pathd: ═════ 汉化安装失败，提示玩家并退出 ═════
21:05:38.146  pathd:   原因: 引擎初始化比汉化补丁更快完成，补丁无法在正确时机安装（建议重试或关闭后台程序）
21:05:38.880  pathd: [方案B] 依赖已就绪，补丁安装移交冻结门          ← 只晚了 0.83 秒
21:05:39.626  pathd:   玩家已确认，正在退出进程
```

而门的**整个意义**就是让引擎停在这里（源码注释原话：「引擎主线程就在本函数里停着，
不存在竞争，单核慢 20 倍也无所谓」）—— 所以等待本来就应该、也是安全的。

### 为什么冷启动正常、热重启失败

引擎跑完 `Application::init` 通常只要 1.7~4 秒，而插件的依赖准备要 3.4 秒以上
（大头是特征码扫描，注释里实测单次全模块扫描 3.5~4.9 秒）。

- **冷启动**：文件缓存冷、驱动初始化慢 ⇒ 引擎更慢 ⇒ 门触发时依赖已经好了 ⇒ 成功
- **热重启**：prefetch + 文件缓存命中 ⇒ 引擎变快 ⇒ 引擎先撞到门 ⇒ F1/F2

两者是**赛跑**，胜负全看当次启动快慢 —— 这正是"有时好有时坏"的来源。

## 4. 修复（三处）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `pathd.cpp:3089` | 对话框改 `MessageBoxW` + UTF-8→UTF-16 |
| 2 | `pathd.cpp:2514` | 门发现依赖未就绪时**原地等待**（10 ms 轮询，上限 20 秒），不再立刻弹框 |
| 3 | `pathd.cpp:3678` | 冻结门**调到 GfxServer hook 之前**安装（原来排在它后面，白晚 1.4~2.0 s） |

改动 2 的核心：

```cpp
if (InterlockedCompareExchange(&g_initDepsReady, 1, 1) == 0) {
    const DWORD tWait0 = GetTickCount();
    Logf("pathd: [冻结门] Init 依赖尚未就绪 —— 原地等待（引擎主线程已停在门里，等待是安全的）");
    while (InterlockedCompareExchange(&g_initDepsReady, 1, 1) == 0) {
        if (GetTickCount() - tWait0 > 20000) break;      // 20 秒才判真失败
        Sleep(10);
    }
    // 等到了 → 继续装配；超时 → 才走 FatalInstallFailure
}
```

### 为什么"等待"不会死锁

- 等待的只是引擎**主线程**（这正是门的设计意图），依赖准备跑在独立的 InitThread 上
- InitThread 的依赖工作全是本地的：特征码扫描、读包文件、读全局变量；
  唯一会调引擎的是**分配器自检探针**（取 `MemoryManager` 的临界区）
- 门的位置是函数收尾（`mov eax,1; pop ebx`），**不持有**该临界区
- 佐证：修复前的成功运行里，门内的 `InstallPatches()` + `PathD_AssembleAll()`
  本来就要用引擎分配器挂图集页表（`pathd.cpp` 注释：必须用引擎堆分配，
  否则 free 无法配对）—— 也就是说"门内另一个线程用引擎分配器"这条路一直是通的

### 顺序调换的安全性核对

门的代码洞只引用 `PathD_InitExitGate` 和自身，与 GfxServer hook 无依赖：

```asm
60                 pushad
B8 <imm32>         mov  eax, PathD_InitExitGate
FF D0              call eax
61                 popad
B8 01 00 00 00     mov  eax, 1          ; 恢复被覆盖的原指令
E9 <rel32>         jmp  0x5AA38D
```

## 5. 验证（实机连续 3 次）

| 运行 | 早期注入耗时 | 门接管 | 等待 | 放行（门内总耗时） | 结果 |
|---|---|---|---|---|---|
| `211841` | 1141 ms | 21:18:46.032 | — | 6250 ms | ✅ 汉字正常 |
| `211906` | 2235 ms | 21:19:10.509 | **500 ms** | 6422 ms | ✅ 汉字正常 |
| `211929` | **312 ms** | 21:19:33.288 | — | 6016 ms | ✅ 汉字正常 |
| （修复前成功样本 `210419`） | 704 ms | 21:04:34.584 | — | 7500 ms | ✅（侥幸赢下赛跑） |
| （修复前失败样本 `210533`） | 2688 ms | 21:05:47.348 | 不等 | — | ❌ 弹框退出 |
| （修复前失败样本 `210633`） | 3875 ms | **无接管行** | — | — | ❌ F2 静默失败 |

`211906` 那次的日志正是 F1 的复活证明：

```
[21:19:10.546] pathd: [冻结门] Init 依赖尚未就绪 —— 原地等待（引擎主线程已停在门里，等待是安全的）
[21:19:11.048] pathd: [冻结门] 依赖就绪（等待了 500 ms），继续装配
```

修复前这里会直接弹框退出；现在等了 500 ms 后正常装配，日志 24 753 字节

另外 `211929` 那次「早期注入 312 ms」也反映出改动 3 的效果：门装在最前面，
后面那些慢活不再推迟门的落地。

## 6. 代价与回退

| 项 | 说明 |
|---|---|
| 代价 | 引擎在进主循环前多停 0.5~3 秒（门内总耗时约 6 秒，其中大部分是本来就有的装配） |
| 现象 | 启动时黑屏略长，属设计行为，不是卡死 |
| 回退 | `update\hta_chs.asi.bak_20261007_2111_before_gatefix`（按时间戳命名的备份）；旧的 `hta_chs.asi.stable-20261007` 也还在 |
| 若仍失败 | 看日志：出现「已等待 N ms，依赖仍未就绪」= 依赖超过 20 秒（真异常）；出现「装了门但没有接管行」= F2 残余，需再提前门的安装或给 `WriteBlockSafe` 加快路径 |
